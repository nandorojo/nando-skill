## Architecture decision

The feature package can contain two distinct roles: portable product UI and the host adapters that compose it. `features/notes/react` never imports `features/notes/next` or Electron siblings. Multiple Next clients can reuse a note adapter while supplying different capabilities. Generic hydration, query providers without app composition, and framework primitives belong below features; product-wide provider composition may remain in `features/app/<host>`. Use `rsc` when a capability has no Next dependency.

The root skill now prominently describes the goal as “Ruby on Rails for JavaScript”: coherent conventions across N clients and useful abstraction levels. This does not require generating all possible layers or platform variants for every product.

## Verification and next eval

The changes are skill documentation and illustrative code, not a repaired or runnable eval app. Whitespace, local reference targets/heading anchors, and balanced code fences pass. The official skill validator could not start because PyYAML is unavailable in both installed Python runtimes; a fallback check confirmed unchanged simple frontmatter and valid name/description constraints. Cross-reference examples were reviewed for contradictory guidance. The added CI rules and bundle gates are specified implementation work, not installed checks.

A future greenfield eval should exercise two independently imported pages; public and private absolute resolution in a packed consumer; thin app manifests; portable UI with/without RSC prefetch; loaded content during refresh failure; list pagination failure; ordinary and Suspense state compositions; exhaustive typed recovery; and patch/reset/replace without bypassing draft lifecycle rules. Use real production builds to assess tree shaking. Preserve this existing eval for comparison.

## Follow-on: context metadata and route filenames

- **Submission in public state was skill-led.** The composer schema and React prose explicitly grouped editable text, lifecycle, and submission eligibility into `ComposerState`. The correction keeps controllable draft values in `state`, operations in `actions`, and submission lifecycle/errors, `canSubmit`, and input refs/capabilities in `meta`. Internal controller state machines remain valid; this is the public context contract. Updated contract, input/submit components, and mock examples together.
- **The route component has an indirect Next dependency.** `notes/next/messages.tsx` calls `useRouteNoteId`; that hook imports `useParams` from the owned Next navigation adapter. It cannot move unchanged to shared React. Its resolved-ID/provider/screen composition can: the shared component accepts a flat ID, while the small Next adapter only reads that ID and renders the shared component. Platform folders should contain only actual host adaptation, including transitive dependencies.
- **The misleading filename was seeded by our example.** The previous skill used `chat/next/messages.tsx` for `RouteChatMessages` in three references. Grok adapted the export to `RouteExistingNote` while retaining `messages.tsx`. The example encouraged a loose filename/export relationship, and the model carried that stale domain name forward. Updated sketches use `route-chat-messages.tsx`, and the naming/enforcement guidance explicitly rejects `messages.tsx` for `RouteExistingNote`.

These follow-on changes also leave the eval untouched.
